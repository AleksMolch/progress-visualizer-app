## 1. Что требуется сделать

1. Существующий дизайн назвать **«Минимализм»**, идентификатор `minimalism`. Сохранить его исходным и значением по умолчанию для существующих установок.
2. Добавить **«Liquid Glass»**, идентификатор `liquid-glass`: стеклянная нижняя навигация и согласованное оформление карточек. Это премиальный ВИЗУАЛЬНЫЙ стиль; задача не включает оплату, блокировку функций или IAP.
3. Добавить **«Галерея»**, идентификатор `gallery`: оформление, вдохновлённое Wolt Clone Simon Grimm — крупные изображения, выраженная типографическая иерархия, светлые поверхности, мягкие скругления, бирюзовый акцент. Предусмотреть тёмный вариант.
4. Добавить переключение оформления внутри существующего экрана настроек. Выбор сохраняется локально и применяется без перезапуска.
5. Сохранить отдельный выбор цветового режима: системный / светлый / тёмный. Оформление и цветовой режим — независимые настройки.
6. В камере добавить переключение обычного наложения ↔ призрак с видимостью 90% по нажатию на свободную область видоискателя. Кнопки, панели, ползунки, меню, таббар и их зоны касания не должны запускать этот жест.
7. Написать и реально выполнить доступные тесты; выполнить тестовые запуски; обновить русскую документацию.

### Важное допущение о «90%»

В пользовательской формулировке есть неоднозначность: буквальные 90% прозрачности соответствуют `opacity: 0.1`, но почти полный показ старого снимка для позиционирования соответствует `opacity: 0.9`.

**Для этого задания принят второй смысл: видимость старого снимка 90%, `opacity: 0.9`.** В интерфейсе писать «Видимость призрака», а не двусмысленное «Прозрачность». Принято переключение по одиночному нажатию, повторное нажатие возвращает обычный режим; НЕ удержание. При первом отчёте явно сообщи владельцу об этих допущениях. Если владелец уточнит другой смысл, исправь контракт и тесты до реализации жеста.

- Expo GlassEffect: https://docs.expo.dev/versions/latest/sdk/glass-effect/
- Expo BlurView: https://docs.expo.dev/versions/latest/sdk/blur-view/
- Expo JavaScript Tabs: https://docs.expo.dev/router/advanced/tabs/
- Expo Native Tabs: https://docs.expo.dev/router/advanced/native-tabs/
- Expo Camera: https://docs.expo.dev/versions/latest/sdk/camera/
- Apple Materials: https://developer.apple.com/design/human-interface-guidelines/materials
- Gesture Handler Tap: https://docs.swmansion.com/react-native-gesture-handler/docs/gestures/tap-gesture/
- Reanimated accessibility: https://docs.swmansion.com/react-native-reanimated/docs/guides/accessibility/
- React Native AccessibilityInfo: https://reactnative.dev/docs/accessibilityinfo
- Zustand persist: https://zustand.docs.pmnd.rs/integrations/persisting-store-data

`latest` со временем меняется: перед кодом сопоставить документацию с SDK и типами проекта.

Apple рекомендует Liquid Glass прежде всего для функционального слоя навигации и контролов, а не для всего контента. Поэтому фотографии остаются обычными изображениями; стеклянное оформление карточки создают рамка, подложка/подпись и область действий, но не размытие самого снимка.

`GlassView` доступен на поддерживаемых iOS 26+ и зависит от условий сборки. Версии ОС самой по себе недостаточно. В актуальной документации есть проверки `isGlassEffectAPIAvailable()` и `isLiquidGlassAvailable()`; использовать их только после проверки наличия в установленном пакете.

`GlassView` на неподдерживаемой платформе превращается в обычный View — это НЕ готовый красивый fallback. Его надо задать явно. Также наличие API не означает, что пользователь разрешил прозрачность: учитывать Reduce Transparency отдельно.

Документация предупреждает о проблеме `opacity: 0` у GlassView и его родителей. Не делать общий fade-out оболочки, содержащей native glass. Анимация opacity призрака относится к обычному изображению, не к стеклянным поверхностям.

## 5. Контракт оформления и настроек

### 5.1. Идентификаторы

Добавить в существующую модель настроек поле `designTheme`. Концептуальный TypeScript-контракт, не готовый патч:

```ts
/** Назначение: стабильные идентификаторы визуального оформления. */
export type DesignThemeId = 'minimalism' | 'liquid-glass' | 'gallery';
```

В `AppSettings`:

- `designTheme: DesignThemeId`, default `minimalism`.
- `themeMode` оставить существующим: system/light/dark.
- Не переименовывать `ghostOpacity` в сохранённых данных ради новой UI-подписи.

`useAppTheme()` расширить обратно совместимо: сохранить `colors` и `scheme`; добавить designTheme и необходимый набор визуальных токенов. Не ломать существующих потребителей.

Разрешение схемы: при system использовать системную, при null — light; иначе уважать явное light/dark. Сейчас themeMode не подключён к провайдеру — это исправить в этой задаче.

### 5.2. Токены

Хранить в `src/theme`, а не размазывать theme-условия по JSX:

- семантические цвета, включая отдельные цвета текста на камере и на акценте;
- радиусы карточек, кнопок, полей и таббара;
- поверхности: solid / frosted / native-glass;
- границы, мягкие тени;
- компактность заголовков и карточек;
- параметры простых анимаций;
- эффективный материал с учётом платформы и accessibility.

Не делать все величины настраиваемыми. Существующие экспортируемые spacing/radii/fontSize сохранить для совместимости; видимые различия новых тем провести через контекстные токены затронутых компонентов.

Не добавлять `key={designTheme}` к Provider, Stack, Tabs, CameraView, спискам или модалкам. Смена темы не должна размонтировать приложение, сбрасывать маршрут, позицию списка, незавершённую форму или заново запрашивать биометрию.

Не интерполировать фон каждого элемента каждую рамку. Мгновенное переключение допустимо; небольшие анимации состояния допустимы при поддержке Reduce Motion.

### 5.3. Сохранение и совместимость со старыми установками

Важная ловушка: настройки находятся во вложенном `settings`. Поверхностный merge persist может заменить весь этот объект старым сохранённым объектом без designTheme.

Обязательно:

1. Написать тест гидратации старой записи, где designTheme отсутствует.
2. Выполнить нормализацию/контролируемое объединение DEFAULT_SETTINGS и сохранённых settings, сохраняя действия стора и прежние значения остальных полей.
3. Валидировать designTheme: неизвестное или неверного типа значение → minimalism.
4. Не превращать настройки биометрии, напоминаний, времени и призрака в defaults при добавлении поля оформления.
5. Сохранить `skipHydration: true` и существующий порядок initializeStorage → rehydrateStores.
6. Если вводится версия persist — реализовать и протестировать миграцию старой версии; увеличение номера без migrate запрещено.
7. Не считать одного migrate достаточным: отсутствие/некорректность нового поля обработать и при merge/нормализации.
8. Не писать временный режим призрака 90% в persist.

Перед гидратацией не показывать кадр случайной темы. Существующий splash/loading gate использовать без нового параллельного процесса инициализации.

## 6. Визуальная спецификация трёх оформлений

### 6.1. Минимализм — текущий интерфейс

Сохранить текущие цвета, типографику, размер карточек и общую компоновку как визуальный baseline. Переименование не означает новый редизайн. Разрешены только общие исправления доступности, согласование цветов системных панелей и необходимые новые настройки/функция призрака.

Не добавлять обложки проектов в минимализм автоматически: новый фото-каталог относится к другим двум темам. Новые возможности при этом одинаково доступны во всех темах.

### 6.2. Liquid Glass — премиальное оформление

**Нижнее меню:** плавающая капсула, скруглённые углы, сдержанная граница, читаемые иконки с подписями, выделение выбранного таба. Те же три вкладки и порядок. Не делать центральную камеру отдельным новым маршрутом/модалкой.

**Карточка проекта:** локальная обложка + имя + количество снимков + существующая дата изменения. Фото остаётся чётким. Стеклянный характер — в рамке, мягкой поверхности подписи и группе действий. Обычный frosted/solid материал для контента предпочтительнее множества native GlassView в списке.

**Настройки:** сгруппированные округлые поверхности, тонкие разделители, те же поля. Не превращать длинные тексты в полупрозрачный белый текст на произвольном фоне.

**Камера:** прозрачные/матовые панели только вокруг существующих контролов. На видоискатель целиком blur не накладывать. Стекло не должно ухудшать точность позиционирования или менять видимость старого снимка.

**Фон:** спокойная светлая или тёмная поверхность; допустимы очень слабые статические цветовые пятна для заметности материала. Без сетевых изображений, постоянных шейдеров и анимированных градиентов.

**Платформы:**

- Поддерживаемая iOS: настоящий native GlassView для панели меню/небольшого функционального слоя.
- iOS без Liquid Glass: BlurView, если поддерживается и уместен, иначе согласованная сплошная поверхность.
- Android: frosted-оформление через проверенный BlurView или сплошная тонированная поверхность. Не обещать нативное стекло Apple.
- Web: CSS/backdrop blur через поддерживаемую реализацию либо сплошная поверхность; без импорта iOS-only модулей в неподдерживаемый runtime.
- Reduce Transparency или недоступный материал: непрозрачная поверхность с сохранением выбранного designTheme.

Один небольшой адаптер материала с явным fallback лучше отдельных копий всех карточек.

### 6.3. Галерея — Wolt-inspired, но не копия Wolt

Переносим следующие элементы:

1. **Фото-ориентированные карточки.** На месте текущих текстовых карточек — карточка с локальным cover-превью, заголовком и второстепенной строкой. Список остаётся вертикальным FlatList с прежним порядком и обработчиками.
2. **Выразительные заголовки.** Более заметный заголовок экрана, спокойные подписи и даты, достаточные интервалы. Не добавлять рекламные слоганы и не занимать экран большим hero-блоком.
3. **Мягкие округлые поверхности.** Контраст белой карточки и холодного светло-серого фона; тёмный аналог с графитовыми поверхностями.
4. **Бирюзовый акцент.** Выделение основных действий и активных состояний, а не окрашивание всех текстов.
5. **Чипы.** Переоформить уже существующие чипы выбора проекта, призрака и сетки. Не добавлять фильтры «фронт/спина», если таких полей нет.
6. **Сдержанные метаданные.** Количество фото и дата — понятная строка или неброский бейдж, без выдуманных рейтингов, скидок, процентов изменения веса.
7. **Кнопки.** Мягкая геометрия, понятное pressed-состояние. Сохраняем заметность переименования/удаления и подтверждение удаления.

Не переносить горизонтальные карусели, sticky-категории и bottom sheet только потому, что они встречаются в референсе: это изменит механику существующих экранов. Их можно обсуждать отдельной задачей, здесь не реализовывать.

**Предлагаемые токены светлого варианта** (наши значения):

- background `#F4F7F9`;
- surface `#FFFFFF`;
- text `#17212B`;
- textSecondary `#53636D`;
- primary `#007C91`;
- primaryText `#FFFFFF`.

**Предлагаемые токены тёмного варианта:**

- background `#0E171C`;
- surface `#17242A`;
- text `#EAF2F4`;
- textSecondary `#AFC0C7`;
- primary `#66D9E8`;
- primaryText `#06252B`.

Расчёт контраста по WCAG для непрозрачных пар: белый на светлом primary ≈ 4.89:1; светлый textSecondary на белой surface ≈ 6.23:1; тёмный primaryText на тёмном primary ≈ 9.68:1. Это не проверка всех состояний: границы, disabled, текст на изображениях и стекле проверить отдельно.

Начальные ориентиры геометрии: радиус крупных карточек 20, кнопок 14, горизонтальный отступ 16–24 логических единиц. Это старт дизайна, а не обязательные размеры на всех экранах. На узком экране и при крупном шрифте допускается адаптация.

## 7. Навигация: как получить стекло без перестройки приложения

### Выбранная стратегия

Оставить существующий `Tabs` из `expo-router/js-tabs` во всех темах. Сначала проверить возможность оформления через существующие tabBarStyle/tabBarBackground/tabBarButton и screenOptions. Если нужная капсула требует отдельного представления, добавить тонкий кастомный tabBar поверх ТЕХ ЖЕ navigation state/descriptors.

Это даёт стеклянный визуальный язык и настоящий стеклянный материал на поддерживаемой iOS, но **не означает полное воспроизведение поведения нативного UITabBar**: системное перетягивание «жидкого» индикатора и автоматическая адаптация цветов могут отличаться.

Не менять условно JS Tabs на NativeTabs при выборе темы: это меняет тип навигатора и создаёт риск потери состояния. Не устанавливать react-native-bottom-tabs и его адаптер из видео без доказанной необходимости.

Если владелец потребует точное поведение native tabs из ролика, оформить это отдельным решением с тестом миграции навигации. В текущей задаче приоритет — существующая структура и сохранность состояния.

### Контракт таббара

- Подписи «Проекты», «Камера», «Настройки» остаются видимыми.
- Иконки использовать существующие Ionicons, не добавлять библиотеку ради смены темы.
- Уважать selected/disabled/pressed, accessibility role/state и testID.
- При кастомном представлении сохранять стандартные tabPress/tabLongPress, preventDefault и поведение повторного выбора. Не вызывать router.push на каждое нажатие, создавая историю дубликатов.
- Тема не должна сбрасывать активный маршрут, параметры, формы и списки.
- Цвета root stack header, экранов, модалок и статус-бара согласовать с принудительным themeMode. `StatusBar style="auto"` сам по себе не выражает принудительно выбранную пользователем тему.

### Safe area и область контента

Плавающий таббар перекрывает содержимое, если не учесть inset. Сейчас `AppScreen` не добавляет отступ для абсолютного таббара; камера имеет фиксированные `bottom: 120` и отдельные отступы затвора.

- Установить одного владельца расчёта перекрытия нижней панели.
- В списках учесть перекрытие в contentContainerStyle и scroll indicators.
- В камере расположить затвор и панель над таббаром; не складывать safe-area inset дважды.
- Не вызывать hook высоты таббара из экрана вне контекста вкладок. При необходимости передавать необязательный inset/контекст с безопасным значением для stack-экранов.
- Внешний контейнер плавающей панели может пропускать касания вне капсулы, но сама капсула и её внутренние отступы блокируют жест камеры.
- На узких устройствах и с крупным текстом controls не должны перекрывать друг друга или полностью закрывать свободный видоискатель.

## 8. Карточки и работа с фотографиями

Обложку проекта вычислять из существующих photos, например через getLatestPhoto по takenAt. Можно добавить необязательные props coverUri/coverAspectRatio к ProjectListItem. Не добавлять coverPhotoId в модель и не проводить миграцию фотографий ради оформления.

Для проекта без фото — нейтральная локальная заглушка на основе существующих иконок. В карточке сохранять name, photoCount, updatedAt и текущие действия. На длинном названии корректное ограничение строк, полное доступное имя для screen reader.

Минимализм использует прежний компактный текстовый вид. Liquid Glass и Галерея могут использовать одну и ту же разметку фото-карточки, различаясь материалами, цветами и радиусами.

В миниатюре допустим `cover`; при сравнении, fullscreen и ghost alignment не менять установленную геометрию изображения ради красоты. Не обрезать сохраняемый файл. Не размывать пользовательскую фотографию ради стеклянного эффекта.

Не загружать все полноразмерные фото в память и не превращать FlatList в ScrollView с map. Не создавать новые постоянные thumbnail-файлы в этой задаче, если без них можно обойтись; новый дисковый кеш требует отдельного анализа удаления и privacy.

Новые обложки повышают видимость приватных снимков на главном экране: не показывать их до существующего допуска к данным. Не обходить BiometricsGate ради preview. Если baseline уже показывает контент до окончания проверки доступа, отметить это как отдельный security blocker, а не рекламировать текущую защиту как доказанную.

## 9. Настройки: переключатель дизайна

В `src/app/(tabs)/settings.tsx` добавить секцию «Оформление» перед существующими настройками либо в логически согласованном месте без новой страницы.

Содержимое:

## 10. Камера: точный контракт быстрого призрака

### 10.1. Два независимых вида состояния

Постоянные настройки остаются существующими:

- `settings.ghostEnabled`;
- `settings.ghostOpacity`.

Временное локальное состояние экрана: например `isReferencePeekActive` (название рекомендательное). Начальное значение false. В Zustand persist/MMKV оно не записывается.

Концептуальная формула, не готовый React-компонент:

```ts
// Назначение: выбрать отображение старого снимка без изменения настроек.
// referenceReady означает, что актуальное изображение успешно загружено.
const visible = referenceReady && (ghostEnabled || isReferencePeekActive);
const effectiveOpacity = isReferencePeekActive ? 0.9 : ghostOpacity;
```

Нужна корректная загрузочная логика: не блокировать первое включение выключенного призрака навсегда из-за того, что его Image ещё не монтирован. Можно хранить состояние загрузки в компоненте отображения; показывать индикатор ожидания, а не ложный статус «90%». Проверка готовности привязана к конкретному URI/id и сбрасывается при их изменении.

### 10.2. Одиночное нажатие

При наличии последнего фото активного проекта, доступной активной камеры и отсутствии захвата/блокирующей модалки:

- Касание с удержанием пальца на свободную область preview включает временный режим 0.9. При этом интерфейс выбора режима прозрачности становится неактивным
- Отпускание палеца возвращает прежний обычный режим.
- Если обычный призрак выключен, быстрый режим всё равно временно показывает старый снимок, а выход снова скрывает его.
- Если исходная ghostOpacity равна 1, быстрый режим задаёт ровно 0.9, а не max(текущее, 0.9).
- Касание с удержанием пальца не снимает фото, не выбирает проект и не меняет сохранённые настройки.
- Сетка остаётся в прежнем состоянии; при усилении ghost не изменять её прозрачность и компоновку.


### 10.3. Контрольные элементы не являются фоном

Не оборачивать весь экран в один Pressable/onTouchEnd. Это приведёт к срабатыванию после нажатия кнопок и перетаскивания ползунка.

Рекомендуемая схема слоёв:

1. CameraView.
2. GhostOverlay и GridOverlay, не перехватывающие касания.
3. Ограниченный preview-слой распознавания Tap, как сосед UI, а не родитель всех контролов.
4. Интерактивные панели/кнопки/селектор проекта поверх слоя жеста.
5. Модалки и нижняя навигация.

Проверить реальный native hit-testing, а не полагаться только на zIndex. Панели, их пустые внутренние отступы, disabled-контролы и hitSlop считаются занятой UI-областью. Прозрачная внешняя оболочка допускает box-none только там, где действительно требуется доступ к фону; внутри панелей прохода жеста быть не должно.

Использовать современный Gesture.Tap + GestureDetector либо уже принятый в проекте подход. Не использовать устаревший PanGestureHandler для одиночного нажатия. При Reanimated callback работать с React-state через корректный bridge/worklet-подход установленной версии; не вызывать setState напрямую из UI-worklet.

Признавать только завершившийся одиночный tap одним пальцем. Смещение/скролл/длинное удержание/отмена/мультитач не переключают режим. Пороги задать явно в одном месте и проверить на устройствах. Не перехватывать системный back-swipe и прокрутку селектора проектов. Если в локальном HEAD уже есть tap-to-focus, конфликт решать явно; не удалять этот функционал молча.

### 10.4. Сброс временного режима

Вернуть isReferencePeekActive в false при:

- уходе с камеры / потере screen focus;
- переходе AppState из active, блокировке или показе защиты;
- смене активного проекта;
- смене/удалении эталонного снимка или ошибке его загрузки;
- начале съёмки, как успешной, так и впоследствии неудачной;
- отзыве camera permission или ошибке камеры;
- открытии блокирующей модалки;
- изменении пользователем ползунка видимости или переключателя обычного призрака.

Обычная отмена незавершённого tap не должна переключать уже выбранный режим. Нажатие любого UI-контрола само по себе не toggle; сброс на shutter/slider/ghost switch производится намеренно обработчиком соответствующего действия.

Смена только визуальной темы при остающейся активной камере не меняет URI, crop и состояние съёмки. При реальном переходе в настройки камера теряет focus и временный режим закономерно сбрасывается.

### 10.5. Отсутствие снимка и ошибки

- Для первого фото проекта жест безопасно ничего не делает, быстрый режим недоступен.
- При загрузке reference не писать «призрак показан», пока его нет; повторные нажатия не должны вызывать очередь переключений.
- При ошибке загрузки — обычный preview и короткое понятное сообщение, возможность сделать новый снимок сохраняется.
- Не показывать эталон предыдущего проекта до загрузки нового; учитывать асинхронную гонку onLoad/onError старого URI.
- Не допускать setState после размонтирования и утечки подписок на AppState/focus/accessibility.

### 10.6. Равнозначное доступное управление

В существующей OverlayControls добавить компактное явное действие «Призрак 90%» с selected-state и подписью для возврата. Это необходимая альтернатива скрытому жесту для VoiceOver/TalkBack/клавиатуры и также объясняет возможность обычным пользователям.

Ползунок переименовать в «Видимость призрака». Временный режим не перемещает thumb на 90% и не переписывает настройку. Пока он активен, подпись сообщает, что сейчас действует временный режим. Если пользователь начинает менять ползунок — выйти из быстрого режима и применить новый обычный уровень.

Не менять существующую стратегию persist ползунка вместе с этим редизайном без отдельной необходимости. Главная гарантия: нажатие фона само не вызывает updateSettings и записи MMKV.

### 10.7. Камера и сохранённые файлы

`takePictureAsync()` и saveCapturedPhoto остаются прежним путём захвата. Призрак, сетка и стеклянные панели НЕ запекаются в сохраняемый кадр. Не заменять съёмку скриншотом View.

Не менять preview aspect ratio, зеркальность и contentFit при переходе в 90%. Если выявлена исходная проблема соответствия ghost/preview, описать её отдельно и не «исправлять» произвольным растяжением.

Документация Expo допускает только один активный preview; при уходе с экрана CameraView должен корректно освобождаться/деактивироваться поддерживаемым способом. Нельзя считать iOS-only `active` универсальным решением для Android. Новый gesture layer не должен удерживать скрытую работающую камеру.

## 11. Производительность, доступность и приватность

- Три оформления работают с теми же данными; переключение не выполняет файловые операции над снимками.
- Не изменять opacity всей иерархии камеры — меняется только изображение призрака.
- Native glass не размножать на каждой ячейке больших списков; фото-карточки могут использовать простые тонированные поверхности.
- Blur на Android проверять по установленному SDK. В современной документации используются BlurTargetView/blurTarget; старый сниппет BlurView из видео может быть недостаточен.
- Не размывать Android camera surface «любой ценой»: если композитинг не поддерживается или медленный — сплошные/матовые панели. Это допустимый fallback.
- Учитывать Reduce Motion и Reduce Transparency; обновление их системных значений обработать доступными подписками или документировать ограничения API. useReducedMotion сам по себе может отражать лишь состояние при старте.
- Интерактивные зоны: ориентир не меньше 44 pt на iOS и 48 dp на Android; масштабирование текста без обрезки главных действий.
- Contrast минимум 4.5:1 для обычного текста и 3:1 для крупного; проверять также реальные фотографии под стеклом. Цвет из палитры не гарантирует контраст с динамическим фоном.
- Явные нажатия, focus и выбранный вариант обозначать не только цветом.
- Нет загрузки Unsplash-картинок, сетевых font CDN и сторонних SDK из референсов.
- Скриншоты/видеозаписи тестов — только синтетические фотографии; пользовательские снимки, пути к ним и секреты не отправлять ИИ-провайдеру, в CI-логи или публичные issues.
- Не менять OTA, privacy policy, backup-конфигурацию и сетевую политику под предлогом оформления. Обнаруженные существующие проблемы зарегистрировать отдельно; не объявлять абсолютную безопасность без аудита.

## 15. Обязательные тесты и приёмочные сценарии

### 15.1. Unit

1. Старые settings без designTheme → minimalism; прежние поля сохранены.
2. Неизвестный theme ID → minimalism, без исключения и потери настроек.
3. Запись/гидратация каждого из трёх дизайнов; hydrate реально вызывается с учётом skipHydration.
4. system/light/dark выбираются независимо от designTheme; null systemScheme даёт светлый режим.
5. Резолвер возвращает полный набор токенов для каждой пары.
6. Capability policy: unsupported API/OS, Reduce Transparency → читаемый fallback, выбранный designTheme не меняется.
7. Быстрый призрак: initial false → tap true → tap false, effectiveOpacity 0.9 в активном режиме.
8. ghostEnabled=false → временно visible, после выхода снова hidden.
9. Обычная opacity 0/0.5/1 сохраняется; быстрый режим всегда ровно 0.9.
10. Нет фото/нет permission/захват/модалка → недоступное переключение.
11. Смена проекта/эталона/focus/AppState/reset-control → выход; устаревшая загрузка изображения не оживляет старый эталон.
12. Tap не вызывает updateSettings/MMKV write; capture вызывает прежний saveCapturedPhoto.

Моки native API нужны, но они не доказывают реальный blur, правильность касаний и съёмки.

### 15.2. Компонентные

- Выбор оформления обновляет selected-state, не удаляет разделы биометрии/напоминаний.
- Модалка переименования и существующие кнопки работают во всех темах.
- Проект без фото и с недоступным URI не ломает карточку.
- Press по shutter, selector, grid, slider и табу не вызывает toggle-reference.
- Доступная кнопка 90% даёт тот же результат, что и фон.
- Поддерживаются loading/error и сброс URI.

### 15.3. На устройстве/эмуляторе — обязательно для приёмки

- Нажатие именно на свободный фон, по отступам панели, краю кнопки/hitSlop и disabled-кнопке.
- Перетаскивание ползунка и горизонтальная прокрутка проектов не включают режим.
- Повторные быстрые tap, длинное касание, мультитач и отмена не вызывают застревание.
- Уход в настройки/фон, возвращение, смена проекта и новый снимок правильно сбрасывают режим.
- Сохранённый снимок не содержит призрак, сетку, glass и UI.
- Glass/fallback реально читаемы; элементы не исчезают после смены темы и сворачивания.
- Нижняя панель не перекрывает затвор и последний элемент списка.
- Выбор темы сохраняется после kill/relaunch и обновления поверх старой установки, не меняя фото.
- После циклического переключения всех тем не теряются выбранный проект, порядок фото, форма переименования и маршрут.
- Крупный шрифт, VoiceOver/TalkBack, Reduce Motion/Transparency; на web — клавиатура.
- Скролл и камера оцениваются на реальном Android и iOS; не обещать FPS по результатам Jest или dev-сборки.

Если iOS 26+ недоступна, native Liquid Glass остаётся непроверенным, даже если fallback работает. Камера в симуляторе не заменяет тест физического устройства.

### 15.4. Регрессия существующих функций

Проекты create/rename/delete; фото capture/view/delete; сравнение бок-о-бок/слайдер; zoom; timelapse; export; напоминания; защита доступа; поддержка; работа без интернета. Не удалять эти функции потому, что их нет в референсах.

### 15.5. Команды

Выполнять из существующего проекта с npm и актуальным lock-файлом. В чистом рабочем окружении восстановление зависимостей — `npm ci`; оно выполняет package lifecycle scripts, поэтому соблюдать разрешения среды.

```bash
# Проверяет TypeScript без генерации кода.
npm run typecheck

# Проверяет исходники существующей конфигурацией Expo ESLint.
npm run lint

# Запускает Jest однократно, последовательно и в CI-режиме.
npm test -- --runInBand --ci

# Проверяет версии и конфигурацию Expo; не заменяет запуск приложения.
npx expo-doctor
```

Script doctor в исследованном package.json вызывает expo-doctor, но пакет не указан среди зависимостей. Проверить доступность команды; не выдавать ошибку отсутствующего executable за несовместимость приложения.

```bash
# Локальные native-запуски: нужны SDK/эмуляторы и разрешения окружения.
npm run android
npm run ios

# Web smoke-тест: не доказывает функциональную эквивалентность native.
npm run web

# Проверка web bundling, если web поддерживается локальным HEAD.
npx expo export --platform web
```

iOS локально требует macOS/Xcode. EAS не обязателен для локальной сборки. Не предлагать изменить ОС или SDK втихую. Долгоживущий Metro-процесс не означает успешный UI-тест: зафиксировать, что экран действительно открыт и сценарий выполнен.

Результаты: PASS / FAIL / BLOCKED / NOT_RUN. Для каждого — команда/сценарий, платформа, commit, код завершения где применимо, фактический результат. Непройденная обязательная проверка не становится PASS от объяснения её отсутствия.
