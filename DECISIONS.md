### 2026-08-21 — Корень Expo Router: /src/app вместо /app

Контекст:

Шаблон Expo SDK 57 размещает корень Expo Router в `/src/app`, а alias `@/*`
указывает на `./src/*`. Изначальный черновик ARCHITECTURE.md предполагал
корневой каталог `/app`.

Решение:

Оставить `/src/app` (как в шаблоне SDK 57) и обновить ARCHITECTURE.md.

Альтернативы:

Перенести роутер в корневой `/app` и перенастроить alias `@/*`.

Почему выбрано это решение:

Не бороться со стандартом SDK 57, меньше конфигурации и меньше расхождений
с будущими версиями Expo.

Риски:

Незначительное расхождение с привычной структурой Expo Router. Снижается за счёт
актуального ARCHITECTURE.md.

Статус:

Принято.

### 2026-08-21 — Отказ от gluestack-ui: собственная UI-система

Контекст:

gluestack-ui v5 сменил архитектуру: требует NativeWind v5 (находится в
`5.0.0-preview.4`) + Tailwind CSS v4 (PostCSS/lightningcss, правки
`metro.config.js`/`babel.config.js`). Поверх нового Expo SDK 57 это даёт
высокий риск несовместимости.

Решение:

Отказаться от gluestack-ui. Использовать собственную лёгкую UI-систему:
дизайн-токены в `/src/theme` + базовые компоненты (AppText, AppButton,
AppScreen, AppCard) на React Native StyleSheet.

Альтернативы:

- legacy gluestack «themed» (`@gluestack-ui/themed` + `@gluestack-style/react`);
- gluestack v5 + NativeWind v5 (preview).

Почему выбрано это решение:

Соответствует принципам YAGNI и «простое решение лучше сложного»; нет
зависимости от preview-библиотеки и шага сборки Tailwind.

Риски:

Придётся реализовывать компоненты, которые gluestack даёт из коробки.
Компенсируется небольшим набором нужных компонентов.

Статус:

Принято (подтверждено пользователем).

### 2026-08-21 — Без react-native-edge-to-edge (нативно в RN 0.86)

Контекст:

В плане был `react-native-edge-to-edge` для edge-to-edge отображения.
RN 0.86 (Expo SDK 57) включает edge-to-edge нативно (Android 15+ по умолчанию),
и пакет отсутствует в bundledNativeModules Expo.

Решение:

Не подключать `react-native-edge-to-edge`; использовать нативный edge-to-edge
и `react-native-safe-area-context` для отступов.

Альтернативы:

Подключить `react-native-edge-to-edge`.

Почему выбрано это решение:

Нет причины добавлять библиотеку, чья функция уже встроена в платформу.

Риски:

Минимальны.

Статус:

Принято.

### 2026-08-22 — Хранение фото только в sandbox приложения

Контекст:

Нужно решить, где физически хранятся файлы фотографий прогресса.
Приватностная модель (CONSTITUTION.md) требует: фото и метаданные хранятся
только на устройстве, без автосохранения в галерею и без облака.

Решение:

Фото хранятся в document-директории приложения
(`Paths.document/photos/<projectId>/<uniqueName>.<ext>`). Используется новый
API expo-file-system (SDK 54+): классы `Directory`, `File`, `Paths`.
Запись в общую галерею не выполняется автоматически ни при каком сценарии —
экспорт возможен только по явному действию пользователя (Фаза 13).

Альтернативы:

- expo-media-library для хранения — отклонено (галерея = вне sandbox).
- legacy API expo-file-system (`FileSystem.documentDirectory`,
  `copyAsync`) — отклонено: помечен как legacy, в SDK 57 рекомендуется
  новый объектный API.

Почему выбрано это решение:

Полное соответствие приватностной модели: файлы доступны только приложению,
OS может очистить их только вместе с приложением, нет «утечки» в галерею.

Риски:

document-директория недоступна пользователю через Files-приложение напрямую —
это ожидаемое поведение sandbox, но пользователь не увидит фото вне приложения
без явного экспорта.

Статус:

Принято.

### 2026-08-22 — Минимальные разрешения камеры (без микрофона и сканера)

Контекст:

expo-camera по умолчанию включает RECORD_AUDIO на Android и запрашивает доступ
к микрофону, а также тянет код сканера штрих-кодов. Приложению нужна только
фотосъёмка — запись видео и сканирование не входят в продукт.

Решение:

В конфигурации плагина expo-camera отключены: `microphonePermission` (false),
`recordAudioAndroid` (false) и `barcodeScannerEnabled` (false). Оставлен только
запрос `NSCameraUsageDescription` на iOS.

Альтернативы:

Оставить настройки по умолчанию (микрофон + RECORD_AUDIO + сканер).

Почему выбрано это решение:

Соответствует принципу минимальных разрешений из CONSTITUTION.md: не запрашивать
доступы, которые не нужны для функции, и не тянуть лишний нативный код.

Риски:

При будущей функции «запись видео для timelapse» потребуется вернуть разрешение
микрофона/аудио — отдельное осознанное решение.

Статус:

Принято.

### 2026-08-24 — Локальные напоминания: только on-device, без push и без пикера времени

Контекст:

Фаза 11 требует локальные напоминания без сервера. Нужно было решить: (1) как
планировать напоминание, (2) нужен ли конфиг-плагин expo-notifications,
(3) как дать пользователю выбрать время без добавления новой нативной
зависимости.

Решение:

- Используются только ЛОКАЛЬНЫЕ уведомления через `expo-notifications`
  (триггер `DailyTriggerInput` — ежедневно в час/минуту). Никакого push-сервера,
  токенов или сетевых запросов — это соответствует CONSTITUTION.md.
- Конфиг-плагин `expo-notifications` в `app.json` НЕ добавляется: он нужен только
  для remote push (entitlement `aps-environment` на iOS) и Android-иконки/звуков.
  Для локальных уведомлений он не требуется, а `aps-environment` без push был бы
  вводящим в заблуждение. Android-разрешение `POST_NOTIFICATIONS` уже объявлено
  в манифесте самой библиотеки.
- Выбор времени — предустановленные варианты («09:00», «13:00», «18:00»,
  «20:00») вместо нативного time-picker: это не требует новой зависимости
  (`@react-native-community/datetimepicker`), а для MVP достаточно.
- Логика уведомлений вынесена в storage-слой (`src/storage/notifications.ts`),
  UI не обращается к expo-notifications напрямую. Парсинг времени — чистая
  функция `parseReminderTime` в `/src/utils`.

Альтернативы:

- Нативный time-picker через `@react-native-community/datetimepicker` — отклонено
  (лишняя нативная зависимость, YAGNI).
- Добавить конфиг-плагин expo-notifications — отклонено (нужен только для push).

Почему выбрано это решение:

Минимальные разрешения и зависимости, полное соответствие приватностной модели.
Ежедневное локальное напоминание покрывает сценарий «не забыть сделать фото»
без какого-либо сетевого взаимодействия.

Риски:

- Выбор времени ограничен пресетами; при желании пользователя в будущем можно
  добавить пикер (осознанное расширение).
- iOS не позволяет повторно запросить разрешение после отказа — пользователь
  должен включить уведомления в настройках устройства (обработано подсказкой).

Статус:

Принято.

### 2026-08-22 — Сравнение фото: свайп-лента на FlatList + pinch на Reanimated

Контекст:

Для Фазы 9 нужно было выбрать механизм «свайпа между фото» в полноэкранном
просмотрщике и способ реализации сравнения «до/после».

Решение:

- Свайп между фото — горизонтальный `FlatList` с `pagingEnabled` и
  `getItemLayout` (нативный скролл). Это надёжнее, чем собственная
  pan-анимация, и не конфликтует с жестами внутри фото.
- Pinch-to-zoom каждого фото — Reanimated 4 + Gesture Handler 2
  (`Gesture.Pinch` + `Gesture.Pan` через `Gesture.Simultaneous`).
- Сравнение «до/после» — перетаскиваемый разделитель (`Gesture.Pan` +
  shared value) и режим «рядом» как альтернатива.
- Сравнение всегда сравнивает текущее фото с предыдущим по `takenAt`
  (чистая функция `getPreviousPhoto`), без ручного выбора пары — минимум UI.

Альтернативы:

- Собственная pan-анимация для свайпа между фото — отклонено (конфликт жестов
  со скроллом, сложнее).
- Выбор двух произвольных фото для сравнения — отложено (лишний UI, YAGNI).

Почему выбрано это решение:

Нативный paging-скролл устойчив и не требует отладки жестов; Reanimated
используется там, где действительно нужен (zoom и перетаскивание разделителя).
Сравнение с предыдущим фото соответствует сценарию прогресса.

Риски:

- Pinch-zoom внутри горизонтальной ленты требует проверки на конфликт жестов
  на реальном устройстве (в симуляторе pinch не проверяется — нет multitouch).
- `onAnimatedValueUpdate` warning при первом рендере Reanimated — безвреден.

Статус:

Принято.

### 2026-08-24 — Premium как локальная dev-заглушка; IAP отложен

Контекст:

Фаза 12 требует «подготовить монетизацию без рекламы». Нужно было решить, как
представить premium до подключения платёжной системы.

Решение:

- Premium представлен локальным флагом `premiumEnabled` в `appStore`
  (персистится в MMKV). Это временная dev-заглушка: переключатель на экране
  «Поддержать разработчика» меняет только локальный флаг и не влечёт списаний.
- In-App Purchase НЕ подключается — это потребует отдельного решения владельца
  продукта (и затронет приватностную модель: покупки через Apple/Google).
- Экран «Поддержать разработчика» даёт честное описание: без рекламы,
  без аналитики/трекинга, данные только на устройстве.

Альтернативы:

- Подключить IAP сразу (expo-in-app-purchases / RevenueCat) — отклонено:
  требует отдельного решения и не входит в MVP.
- Не делать premium-заглушку вовсе — отклонено: флаг нужен как точка входа
  для будущего IAP и для честного разграничения в UI.

Почему выбрано это решение:

CONSTITUTION.md разрешает IAP как будущее исключение, но требует отдельного
решения владельца. Локальный флаг даёт задел без внедрения платёжного SDK
и без сетевых запросов (в т.ч. без отправки чека/идентификатора).

Риски:

- Флаг premium пока ни на что не влияет в функциональности приложения.
- При переходе на реальный IAP локальный флаг должен быть дополнен
  server-валидацией покупки (но без передачи фото/контента наружу).

Статус:

Принято.
