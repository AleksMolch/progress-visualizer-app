### 2026-08-21 — Корень Expo Router: /src/app вместо /app

Контекст:

Шаблон Expo SDK 57 размещает корень Expo Router в `/src/app`, а alias `@/*`
указывает на `./src/*`. Изначальный черновик ARCHITECTURE.md предполагал
корневой каталог `/app`.

Решение:

с будущими версиями Expo.

Риски:

Незначительное расхождение с привычной структурой Expo Router. Снижается за счёт
актуального ARCHITECTURE.md.

### 2026-08-21 — Отказ от gluestack-ui: собственная UI-система

Контекст:

gluestack-ui v5 сменил архитектуру: требует NativeWind v5 (находится в
`5.0.0-preview.4`) + Tailwind CSS v4 (PostCSS/lightningcss, правки
`metro.config.js`/`babel.config.js`). Поверх нового Expo SDK 57 это даёт
высокий риск несовместимости.

Решение:

Отказаться от gluestack-ui. Использовать собственную лёгкую UI-систему:
дизайн-токены в `/src/theme` + базовые компоненты (AppText, AppButton,
AppScreen, AppCard) на React Native StyleSheet.

Альтернативы:

- legacy gluestack «themed» (`@gluestack-ui/themed` + `@gluestack-style/react`);
- gluestack v5 + NativeWind v5 (preview).

Почему выбрано это решение:

Соответствует принципам YAGNI и «простое решение лучше сложного»; нет
зависимости от preview-библиотеки и шага сборки Tailwind.

Риски:

Придётся реализовывать компоненты, которые gluestack даёт из коробки.
Компенсируется небольшим набором нужных компонентов.

### 2026-08-22 — Хранение фото только в sandbox приложения

Контекст:

Нужно решить, где физически хранятся файлы фотографий прогресса.
Приватностная модель (CONSTITUTION.md) требует: фото и метаданные хранятся
только на устройстве, без автосохранения в галерею и без облака.

Решение:

Фото хранятся в document-директории приложения
(`Paths.document/photos/<projectId>/<uniqueName>.<ext>`). Используется новый
API expo-file-system (SDK 54+): классы `Directory`, `File`, `Paths`.
Запись в общую галерею не выполняется автоматически ни при каком сценарии —
экспорт возможен только по явному действию пользователя (Фаза 13).

Альтернативы:

- expo-media-library для хранения — отклонено (галерея = вне sandbox).
- legacy API expo-file-system (`FileSystem.documentDirectory`,
  `copyAsync`) — отклонено: помечен как legacy, в SDK 57 рекомендуется
  новый объектный API.

Почему выбрано это решение:

Полное соответствие приватностной модели: файлы доступны только приложению,
OS может очистить их только вместе с приложением, нет «утечки» в галерею.

Риски:

document-директория недоступна пользователю через Files-приложение напрямую —
это ожидаемое поведение sandbox, но пользователь не увидит фото вне приложения
без явного экспорта.

Статус:

Принято.

### 2026-08-24 — Локальные напоминания: только on-device, без push и без пикера времени

Контекст:

Фаза 11 требует локальные напоминания без сервера. Нужно было решить: (1) как
планировать напоминание, (2) нужен ли конфиг-плагин expo-notifications,
(3) как дать пользователю выбрать время без добавления новой нативной
зависимости.

Решение:

- Используются только ЛОКАЛЬНЫЕ уведомления через `expo-notifications`
  (триггер `DailyTriggerInput` — ежедневно в час/минуту). Никакого push-сервера,
  токенов или сетевых запросов — это соответствует CONSTITUTION.md.
- Конфиг-плагин `expo-notifications` в `app.json` НЕ добавляется: он нужен только
  для remote push (entitlement `aps-environment` на iOS) и Android-иконки/звуков.
  Для локальных уведомлений он не требуется, а `aps-environment` без push был бы
  вводящим в заблуждение. Android-разрешение `POST_NOTIFICATIONS` уже объявлено
  в манифесте самой библиотеки.
- Выбор времени — предустановленные варианты («09:00», «13:00», «18:00»,
  «20:00») вместо нативного time-picker: это не требует новой зависимости
  (`@react-native-community/datetimepicker`), а для MVP достаточно.
- Логика уведомлений вынесена в storage-слой (`src/storage/notifications.ts`),
  UI не обращается к expo-notifications напрямую. Парсинг времени — чистая
  функция `parseReminderTime` в `/src/utils`.

Альтернативы:

- Нативный time-picker через `@react-native-community/datetimepicker` — отклонено
  (лишняя нативная зависимость, YAGNI).
- Добавить конфиг-плагин expo-notifications — отклонено (нужен только для push).

Почему выбрано это решение:

Минимальные разрешения и зависимости, полное соответствие приватностной модели.
Ежедневное локальное напоминание покрывает сценарий «не забыть сделать фото»
без какого-либо сетевого взаимодействия.

Риски:

- Выбор времени ограничен пресетами; при желании пользователя в будущем можно
  добавить пикер (осознанное расширение).
- iOS не позволяет повторно запросить разрешение после отказа — пользователь
  должен включить уведомления в настройках устройства (обработано подсказкой).

Статус:

Принято.

### 2026-08-22 — Сравнение фото: свайп-лента на FlatList + pinch на Reanimated

Контекст:

Для Фазы 9 нужно было выбрать механизм «свайпа между фото» в полноэкранном
просмотрщике и способ реализации сравнения «до/после».

Решение:

- Свайп между фото — горизонтальный `FlatList` с `pagingEnabled` и
  `getItemLayout` (нативный скролл). Это надёжнее, чем собственная
  pan-анимация, и не конфликтует с жестами внутри фото.
- Pinch-to-zoom каждого фото — Reanimated 4 + Gesture Handler 2
  (`Gesture.Pinch` + `Gesture.Pan` через `Gesture.Simultaneous`).
- Сравнение «до/после» — перетаскиваемый разделитель (`Gesture.Pan` +
  shared value) и режим «рядом» как альтернатива.
- Сравнение всегда сравнивает текущее фото с предыдущим по `takenAt`
  (чистая функция `getPreviousPhoto`), без ручного выбора пары — минимум UI.

Альтернативы:

- Собственная pan-анимация для свайпа между фото — отклонено (конфликт жестов
  со скроллом, сложнее).
- Выбор двух произвольных фото для сравнения — отложено (лишний UI, YAGNI).

Почему выбрано это решение:

Нативный paging-скролл устойчив и не требует отладки жестов; Reanimated
используется там, где действительно нужен (zoom и перетаскивание разделителя).
Сравнение с предыдущим фото соответствует сценарию прогресса.

Риски:

- Pinch-zoom внутри горизонтальной ленты требует проверки на конфликт жестов
  на реальном устройстве (в симуляторе pinch не проверяется — нет multitouch).
- `onAnimatedValueUpdate` warning при первом рендере Reanimated — безвреден.

Статус:

Принято.

### 2026-08-24 — Экспорт в галерею: write-only и только по явному действию

Контекст:

Фаза 13 добавляет экспорт фото в системную галерею. Это исключение из
sandbox-модели хранения, разрешённое CONSTITUTION.md только «по явному
действию пользователя». Нужно было выбрать API и набор разрешений.

Решение:

- Используется новый объектный API `expo-media-library` (SDK 57):
  `Asset.create(filePath)`. Устаревшие `saveToLibraryAsync`/`createAssetAsync`
  в SDK 57 выбрасывают ошибку в runtime — не используются.
- Разрешения минимальны (write-only): на iOS добавлен только
  `NSPhotoLibraryAddUsageDescription` (сохранение) через конфиг-плагин с
  `photosPermission: false` (ключ чтения `NSPhotoLibraryUsageDescription`
  НЕ добавляется). На Android задан `granularPermissions: []` (без
  READ_MEDIA_* чтения).
- Экспорт инициируется только кнопкой пользователя на экране просмотра фото.
  Перед экспортом показывается Alert с предупреждением, что фото окажется
  ВНЕ sandbox приложения (в галерее, доступной другим приложениям).
- Логика экспорта/разрешений вынесена в storage-слой
  (`src/storage/mediaLibrary.ts`); UI не обращается к expo-media-library напрямую.

Альтернативы:

- Старый legacy API (`saveToLibraryAsync`) — отклонено: deprecated в SDK 57
  и выбрасывает ошибку в runtime.
- Полный доступ к галерее (read + write) — отклонено: для экспорта чтение
  не нужно, это нарушило бы принцип минимальных разрешений.

Почему выбрано это решение:

Соответствие CONSTITUTION.md: экспорт строго по явному действию, внутреннее
хранение остаётся sandbox-first, набор разрешений минимален (только запись).

Риски:

- Плагин expo-media-library на Android безусловно добавляет legacy-разрешения
  `READ_EXTERNAL_STORAGE`/`WRITE_EXTERNAL_STORAGE` (без них не обойтись через
  конфиг) — на Android 10+ они не дают доступа (scoped storage). Проверить
  итоговый набор разрешений в Фазе 15.
- Экспортированное фото больше не контролируется приложением (находится в
  галерее) — это ожидаемо и предупреждается в UI.

Статус:

Принято.

### 2026-08-24 — Timelapse: research (Фаза 14), решение ожидает владельца

Контекст:

Нужно понять, можно ли генерировать видео-timelapse из серии фотографий
прогресса локально, без сервера и без deprecated библиотек (CONSTITUTION.md:
нет cloud AI/ML, всё on-device).

Исследованы варианты (проверено по npm-реестру и docs Expo SDK 57, 2026-08-24):

1. `expo-video` (~57.0.2) — только воспроизведение + извлечение кадров
   (`generateThumbnailsAsync`). НЕТ возможности склеить изображения в видео
   и нет записи. Не подходит.
2. `ffmpeg-kit-react-native` (6.0.2) — npm помечает как deprecated
   («Package no longer supported»), проект FFmpegKit завершён. Тяжёлый нативный
   бинарник + вопросы лицензий (LGPL/GPL). Противоречит запрету deprecated-библиотек.
3. `react-native-ffmpeg` (0.5.2) — deprecated («Not maintained»).
4. `react-native-image-sequence` (0.7.0) — не обновляется с 2022, только
   воспроизводит последовательность кадров, НЕ создаёт видеофайл.
5. `react-native-vision-camera` (5.2.3) — актуальна, но для реалтайм-съёмки
   и frame-processors, не для склейки уже сохранённых фото.
6. Собственный нативный Expo Module (local module) — единственный «чистый»
   on-device путь: iOS `AVAssetWriter` + `AVAssetWriterInputPixelBufferAdaptor`,
   Android `MediaMuxer` + `MediaCodec` (или AndroidX Media3 Transformer с
   поддержкой статичных изображений). Требует custom native code (Swift/Kotlin).

Вывод:

Поддерживаемой НЕ-deprecated JS-библиотеки для генерации видео из фото в текущем
стеке (Expo SDK 57 / RN 0.86) нет. Реализация «по-честному» — это собственный
нативный модуль, что существенно увеличивает объём и риски.

Альтернативы (для MVP):

- Оставить timelapse вне MVP (рекомендуется) — отложить до отдельного решения.
- Лёгкая «псевдо-timelapse» без видеофайла: быстрый слайд-шоу/анимация по фото
  в UI (не создаёт файл, дешевле, но это не настоящий экспортируемый timelapse).

Риски (при реализации нативным модулем):

- Ручное написание Swift/Kotlin, обновление при смене SDK, отладка кодеков
  и ориентации/размера кадров.
- Android-матрица устройств (MediaCodec/MediaMuxer) — тестировать вручную.

Статус:

Принято. Решение владельца (2026-08-24): реализовать «псевдо-timelapse»
(слайд-шоу по фото в UI, без видеофайла). Создание нативного модуля для
генерации настоящего видео отложено — записано в TODO.md как факультативная
задача на будущее (с выводами анализа).

### 2026-09-14 — Три оформления, материал и быстрый призрак (hold-to-peek)

Контекст:

Задание `DESIGN_THEMES_AND_GHOST_TASK.md`: добавить три визуальных оформления
(`minimalism`/`liquid-glass`/`gallery`), независимый цветовой режим и быстрый
показ призрака. Нужно было решить ряд архитектурных вопросов без перестройки
приложения.

Решение:

1. **Одно дерево экранов, три темы через токены.** `AppSettings.designTheme`
   (default `minimalism`) + независимый `themeMode` (`system|light|dark`).
   Токены (палитра, радиусы, материал) резолвятся в `src/theme/design-themes.ts`,
   провайдер отдаёт их через расширенный `useAppTheme()` (обратно совместимо).
2. **JS Tabs сохранены.** Оформление капсулы — через `tabBarStyle`/
   `tabBarBackground`, БЕЗ `react-native-bottom-tabs`/NativeTabs. Смена темы не
   меняет тип навигатора и не сбрасывает состояние.
3. **Материал — один адаптер с fallback.** `AdaptiveSurface`
   (`.tsx` + `.ios.tsx`): native-glass → GlassView (expo-glass-effect), иначе
   BlurView (expo-blur), иначе solid. Reduce Transparency → solid. Вне iOS
   материал сводится к solid без импорта iOS-only модулей.
4. **Без paywall.** Liquid Glass — премиальный визуальный стиль, не блокирует
   функции и не связан с IAP.
5. **Миграция настроек.** `normalizeSettings` + кастомный `merge` в persist:
   старая запись без `designTheme` не затирает defaults, неизвестный ID →
   `minimalism`. `skipHydration` и порядок инициализации не менялись.
6. **Быстрый призрак — hold-to-peek.** Семантика «90%» = видимость 90%
   (`opacity: 0.9`). Удержание пальца на свободной зоне превью включает 0.9,
   отпускание возвращает обычный режим; временное состояние `isPeekActive`
   НЕ пишется в persist. Доступная альтернатива — кнопка «Призрак 90%» (toggle).

Альтернативы:

- NativeTabs / react-native-bottom-tabs — отклонено (меняет тип навигатора,
  риск потери состояния).
- Tap-toggle призрака — отклонено владельцем в пользу hold-to-peek.
- Размножать native GlassView в каждой ячейке списка — отклонено (дорого),
  карточки используют frosted/solid.

Почему выбрано это решение:

Минимальные изменения поверх существующей архитектуры: те же маршруты,
модель фото, приватность и навигация. Визуальные различия — через контекстные

Контекст:

Риски:

- Звук затвора и слайдер/клавиатура требуют проверки на реальных iOS/Android устройствах

2. **Каскадный список проектов — Reanimated, без новых зависимостей.** Задержка
   вынесена в чистую утилиту `src/utils/stagger.ts` (`getStaggerDelay`, шаг 60 мс,
   первые 10 элементов). `ProjectListItem` получает `index`/`animateOnMount`/
   `animationNonce`, анимация `opacity 0→1 + translateY 20→0` с пружиной; экран
   проектов перезапускает каскад при каждом возврате через `useFocusEffect`.
   Элементы после лимита и `reduce motion` показываются мгновенно.
3. **Слайдер сравнения усилен на месте, а не новым компонентом.** Спека предлагала
   новый `enhanced-slider.tsx`, но корректная геометрия (clip вместо сжатия,
   сохранение доли при повороте) уже реализована в `compare-slider.tsx` — новый
   компонент дублировал бы её. Добавлены: intro 0%→100%→50% (1.5s + 0.3s + 0.6s,
   прерывается жестом), доводка пружиной с учётом `velocityX`, handle 44pt с
   иконками `chevron-back/forward`, haptic у краёв через `triggerHaptic` (только при
   `hapticsEnabled`), accessibility (`adjustable` + проценты), reduced motion.
4. **Градиент линии — встроенный RN 0.86 `experimental_backgroundImage`, без
   `expo-linear-gradient`.** Это позволяет не добавлять нативную зависимость ради
   одной косметической детали (спека сама допускала fallback). На New Architecture
   градиент работает на iOS и Android.
5. **Анимированные числа — `AnimatedNumber` на паттерне Reanimated 4.** Спека
   использовала `Animated.addWhitelistedNativeProps`, которого в Reanimated 4 нет.
   Компонент построен на штатном для 4.x паттерне: `createAnimatedComponent(TextInput)`
   + `useAnimatedProps({ text, defaultValue })` (так устроен PerformanceMonitor самой
   библиотеки). Интеграции: статистика проекта (фото/дни), процент ghost overlay в
   камере (25%↔85%), дни между снимками в compare. При reduced motion — мгновенно.
6. **Попутно исправлен сломанный блок в `project/[id]/index.tsx`.** Проверка
   `hasHydrated`/skeleton была по ошибке вставлена внутрь `handleAddPhoto`
   (коммит cf7b03a) — теперь это ранний return в теле экрана, как задумано.

Альтернативы:

- Держать старый звук и снижать системную громкость — запрещено заданием и ненадёжно.
- `expo-linear-gradient` — отклонено: новая нативная зависимость ради одной линии.
- Новый `EnhancedSlider` рядом со старым — отклонено: дублирование геометрии.
- `AnimatedNumber` через `useState` + `useAnimatedReaction` — лишние ре-рендеры;
  выбран TextInput-паттерн Reanimated.

Риски:

- Отсутствие/наличие звука на release APK и OEM-ограничения проверяются только
  вручную на физическом Android (в окружении нет устройства/эмулятора).
- Визуальная приёмка анимаций (каскад, intro слайдера, count-up) — ручная: модель
  не читает скриншоты. Runtime-проверка на симуляторе пройдена (бандл без ошибок).

Статус:

Принято (реализовано; ручная приёмка на устройствах — за владельцем).

### 2026-10-12 — Возврат разрешения CAMERA и полный permission flow камеры

Контекст:

Задание `AI_CODER_CAMERA_FIX_AND_ANIMATED_GRID_LIST.md`, задача 1: на Samsung новый
APK не запрашивал разрешение камеры; в системных настройках приложения отсутствовал
пункт «Камера». Причина подтверждена исходником config plugin: в `app.json` у
`expo-image-picker` стояло `cameraPermission: false`. Плагин трактует это как запрет
разрешения для ВСЕХ библиотек и вызывает `withBlockedPermissions(['android.permission.CAMERA'])`
— в манифест добавляется `tools:node="remove"` для CAMERA, который перебивает
`android.permission.CAMERA` из `android.permissions` и от `expo-camera`
(`node_modules/expo-image-picker/plugin/build/withImagePicker.js`).
Дополнительно `expo-image-picker` по умолчанию (когда `microphonePermission` не задан)
добавлял `android.permission.RECORD_AUDIO`, хотя микрофон приложению не нужен.

Решение:

1. **app.json:** у `expo-image-picker` удалён `cameraPermission: false`, добавлен
   `microphonePermission: false`, сохранён `photosPermission: false`. CAMERA остаётся
   в `android.permissions` и добавляется плагином `expo-camera`; `recordAudioAndroid: false`
   у камеры сохранён. В итоговом манифесте: `android.permission.CAMERA` есть, правила
   `tools:node="remove"` для CAMERA нет, `RECORD_AUDIO` помечен `tools:node="remove"`.
2. **versionCode 1 → 2.** Изменение config plugin не применяется без native-сборки,
   поэтому обязательна чистая генерация (`expo prebuild --clean`) и новый APK.
3. **Полный permission flow** в `src/app/(tabs)/camera.tsx`: чистый резолвер
   `resolveCameraPermissionView` в `src/utils/cameraPermission.ts` (loading / request /
   blocked / granted, покрыт тестами) + экран разрешения: запрос с guard от повторного
   нажатия и текстом «Запрос разрешения…», постоянный отказ → `Linking.openSettings()`
   с обработкой ошибки и повтором, вторичная кнопка «Назад к проектам».
   Автообновление статуса — единственная подписка `AppState`: возврат в `active` вызывает
   `getPermission()` (без автоматического system-диалога). Экраны используют цвета темы,
   safe area и отступ под нижнее меню — контраст и читаемость во всех оформлениях.
4. **Звук затвора** остаётся отключённым (`shutterSound: false`), visual shutter,
   haptic по настройке, `isCapturing` и shutter bridge не изменялись.

Альтернативы:

- Оставить `cameraPermission: false` и дорабатывать runtime-запрос — не поможет:
  разрешение вырезано из манифеста, диалог невозможен.
- Ручные Samsung-specific URI настроек — отклонено, стандартный `Linking.openSettings()`.
- Запросить разрешение автоматически при входе — отклонено: диалог только по явному
  действию пользователя.

Риски:

- Проверка выполняется вручную на физическом Android (Samsung): чистая установка,
  системный диалог, отказ/повтор, возврат из Settings, 10 снимков, тихий затвор.
  В окружении устройства нет — эти пункты остаются за владельцем.
- OEM/региональные прошивки могут принудительно проигрывать звук затвора — не обходим.

Статус:

Принято (реализовано; EAS APK-сборка — отдельным шагом; ручная приёмка за владельцем).

### 2026-10-12 — iPad, онбординг, политика конфиденциальности и миниатюры

Контекст:

Владелец передал `ALTERNATIVE_STORES_REQUIREMENTS.md` (готовность к альтернативным
магазинам) и `IMPLEMENTATION_IPAD_ONBOARDING_PRIVACY_THUMBNAILS.md` с четырьмя
задачами: поддержка iPad, стартовый онбординг, политика конфиденциальности для
магазинов, миниатюры для timeline. Задание требует адаптации к фактической
структуре проекта (компоненты, i18n, storage-слой, новый API expo-file-system).

Решение:

1. **iPad: `ios.supportsTablet: true`.** Ориентация остаётся portrait (как в
   app.json). Требуется новая native-сборка; проверка макетов на iPad — ручная.
2. **Онбординг: флаг `hasCompletedOnboarding` в `AppSettings`** (persist через
   существующий settingsStore/MMKV, без отдельного хранилища). Маршрут
   `/onboarding` с 4 шагами (прогресс, призрак, сравнение, таймлапс); «Пропустить»
   и «Начать» пишут флаг. Гейтинг — `Stack.Protected` (expo-router SDK 57):
   основные экраны доступны только после прохождения, onboarding — только до;
   ручных redirect-эффектов нет. Старые установки без поля увидят онбординг один
   раз (normalizeSettings по умолчанию `false`). Все тексты — в 5 локалях.
3. **Политика конфиденциальности для магазинов.** `PRIVACY_POLICY.md` (EN,
   контакт — al.molch@gmail.com) + существующий `PRIVACY.md` (RU, со ссылкой на EN).
   `docs/privacy-policy.html` подготовлен для GitHub Pages (включаются вручную в
   настройках репозитория; gh CLI в окружении нет). Ссылка приложения берётся из
   `app.json extra.privacyPolicyUrl` и открывается через `Linking.openURL`
   (кнопка в Настройках). Из текста убраны обещания будущего облака — политика
   отражает текущую архитектуру (всё on-device).
4. **Миниатюры timeline: 400px JPEG 0.7 в storage-слое.** Новый API
   `expo-image-manipulator` (~57.0.21, SDK-pinned, добавлен через `expo install`).
   `createPhotoThumbnail(uri)` создаёт `<имя>_thumb.jpg` рядом с оригиналом;
   `PhotoMetadata.thumbnailUri` — optional (старые фото без него). Списки/превью
   используют `getPhotoPreviewUri(photo)` (миниатюра → fallback оригинал);
   viewer/compare/камера остаются на полноразмерных файлах. Удаление фото удаляет
   и миниатюру; удаление проекта — всю папку. Сбой генерации не ломает сохранение
   (фото пишется без миниатюры). Миграция старых фото — `ensureThumbnails()` из
   root layout после гидратации: последовательно, один batched set в store.

Альтернативы:

- Отдельный onboarding-store — отклонено: существующий settingsStore + MMKV решает.
- Ручной redirect в root layout — отклонено в пользу `Stack.Protected`.
- Генерация миниатюр «на лету» при скролле — сложнее и создаёт лаги; миграция при
  старте проще и предсказуемее.
- Хранение миниатюр в отдельной папке — отклонено: суффикс рядом с оригиналом
  упрощает удаление и не ломает правило «папка проекта — всё его фото».
- Дубли i18n-текстов «на будущее» (например, Terms) — отклонено (YAGNI).

Риски:

- Новая native-зависимость (`expo-image-manipulator`) означает: установленный dev
  build и APK v2 БЕЗ пересборки запускать нельзя (модуль отсутствует в native
  части). Нужна native-сборка (EAS/run:ios) перед проверкой.
- Макеты на iPad, скорость генерации миниатюр на большом архиве, показ онбординга
  — проверяются вручную.
- GitHub Pages для политики нужно включить в настройках репозитория; до этого
  `extra.privacyPolicyUrl` указывает на GitHub-rendered markdown (рабочая ссылка).

Статус:

Принято (реализовано; native-сборка и ручная приёмка — отдельным шагом).
