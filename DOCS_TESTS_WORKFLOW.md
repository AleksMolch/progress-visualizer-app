# DOCS_TESTS_WORKFLOW — рабочий процесс кода, тестов и документации

> Этот файл описывает, КАК ИИ-исполнитель должен писать код, тесты, запускать
> проверки, делать тестовые запуски и создавать документацию.
>
> Читается вместе с: AGENTS.md, CONSTITUTION.md, TESTING.md, CODE_STYLE_RU.md.
> Язык всей документации и комментариев — РУССКИЙ.
> Язык кода (имена переменных, функций) — АНГЛИЙСКИЙ.

---

## 1. Общий цикл работы над каждой задачей

Для каждой подзадачи из TODO.md исполнитель проходит один и тот же цикл:

1. Прочитать якорные файлы (см. AGENTS.md).
2. Написать/обновить тест (для логики — сначала тест, TDD).
3. Написать код с документацией на русском (см. CODE_STYLE_RU.md).
4. Запустить проверки (typecheck, lint, test).
5. Сделать тестовый запуск приложения (если задача влияет на UI/native).
6. Обновить документацию (README, README_staff, комментарии).
7. Обновить PROGRESS.md.
8. Сделать коммит.

Ни один шаг не пропускается. Если шаг невозможен — честно записать причину.

## 2. Что писать: код

### Правила

- TypeScript strict, без `any` без комментария-обоснования.
- Каждый файл начинается с шапки-комментария (см. CODE_STYLE_RU.md).
- Каждый логический блок сопровождается кратким пояснением на русском.
- Функции с нетривиальной логикой имеют JSDoc-комментарий на русском.
- Не переусложнять: простой читаемый код важнее «умного».

### Где что лежит

Границы слоёв — строго по ARCHITECTURE.md:

- UI — `/app`, `/src/components`, `/src/features/*/components`
- Состояние — `/src/store`
- Хранилище — `/src/storage`
- Типы — `/src/models`
- Чистые функции — `/src/utils`

## 3. Что писать: тесты

### Инструменты

- Jest + @testing-library/react-native (или то, что идёт с Expo template).
- Тесты лежат рядом с кодом в файлах `*.test.ts` / `*.test.tsx`
  или в папке `__tests__` внутри модуля.

### Что покрывать обязательно

- Модели данных (`/src/models`).
- Zustand-сторы (`/src/store`) — создание/удаление проектов, фото, настройки.
- Storage-обёртки (`/src/storage`) — с замоканным file/MMKV API.
- Чистые функции (`/src/utils`).

### Что НЕ покрывать unit-тестами

- Camera preview, реальные permission-диалоги, биометрию, жесты,
  нативные уведомления — проверяются вручную (manual verification из TODO.md).

### Правило TDD (для логики)

1. Написать тест.
2. Убедиться, что он падает по ожидаемой причине.
3. Написать код.
4. Убедиться, что тест проходит.

### Формат теста (пример структуры)

```typescript
// Тест: создание и удаление проекта в projectStore
// Проверяем, что проект добавляется в состояние и корректно удаляется.

describe('projectStore', () => {
  beforeEach(() => {
    // Сброс состояния перед каждым тестом, чтобы тесты не влияли друг на друга.
  });

  it('создаёт новый проект', () => {
    // Подготовка -> действие -> проверка (Arrange / Act / Assert).
  });

  it('удаляет проект и связанные метаданные фото', () => {
    // ...
  });
});
```

## 4. Как запускать проверки

Все проверки — через npm-скрипты (настраиваются в Фазе 0):

```bash
npm run typecheck   # tsc --noEmit
npm run lint        # eslint .
npm test            # jest
npx expo-doctor     # проверка совместимости зависимостей
```

### Правило

- Исполнитель ОБЯЗАН реально запускать команды, а не «предполагать» результат.
- Нельзя писать «тесты проходят», если команда не запускалась.
- Если проверка невозможна из-за окружения — написать честно:
  `Проверка не выполнена. Причина: ...`

---

## 5. Как делать тестовые запуски приложения

Для задач, влияющих на UI или native-модули:

```bash
npx expo run:ios       # запуск на iOS-симуляторе
npx expo run:android   # запуск на Android-эмуляторе
```

Важно: MMKV, camera и др. native-модули НЕ работают в Expo Go —
только development build.

### Что фиксировать после тестового запуска

- Приложение запустилось без краша: да/нет.
- Проверяемый сценарий работает: да/нет.
- Замеченные проблемы (лаги, визуальные баги, ошибки в консоли).
- На какой платформе проверено (iOS / Android / обе).

Если окружение для запуска недоступно (нет симулятора) — честно указать это
и пометить задачу как требующую ручной проверки пользователем.

## 6. Документация: какие файлы и когда

### 6.1. Комментарии в коде (постоянно)

В каждом создаваемом/изменяемом файле — по правилам CODE_STYLE_RU.md:
- шапка файла (назначение и функции);
- пояснения по каждому логическому блоку.

Это делается СРАЗУ при написании кода, не откладывается.

### 6.2. README.md (пользовательский, для git)

- Основа — файл README.template.md.
- Обновляется по мере появления функций.
- Язык — русский, тон — для конечного пользователя.
- Финализируется в Фазе 15.

### 6.3. README_staff.md (для команды поддержки)

- Основа — файл README_staff.template.md.
- Детальное техническое описание для поддержки.
- Обновляется при каждом значимом изменении архитектуры/функций.
- Язык — русский, тон — для инженера поддержки.

### 6.4. MAINTENANCE_AI.md (для ИИ поддержки и развития)

- Уже подготовлен как отдельный файл.
- Исполнитель ОБНОВЛЯЕТ его при изменении архитектуры, добавлении модулей,
  изменении процессов сборки/публикации, при планах по web-версии.

### 6.5. DECISIONS.md и PROGRESS.md

- DECISIONS.md — при каждом нетривиальном архитектурном решении.
- PROGRESS.md — в конце каждой фазы.

## 7. Синхронизация кода и документации

Правило: **код и документация меняются в одном коммите.**

Если изменилась функция — обновляются:
1. комментарии в коде;
2. соответствующий раздел README.md (если видно пользователю);
3. соответствующий раздел README_staff.md (техдетали);
4. при необходимости — MAINTENANCE_AI.md.

Расхождение кода и документации считается ошибкой, а не «мелочью».

## 8. Definition of Done (когда задача действительно готова)

Подзадача считается завершённой, только когда выполнено ВСЁ:

- [ ] Код написан по CODE_STYLE_RU.md (шапка + пояснения по блокам).
- [ ] Тесты написаны (где применимо) и реально запущены.
- [ ] typecheck, lint, test — зелёные (или причина честно записана).
- [ ] Тестовый запуск выполнен (для UI/native) или отмечено, что невозможно.
- [ ] Документация обновлена (README / README_staff / комментарии).
- [ ] PROGRESS.md обновлён.
- [ ] Коммит сделан с понятным сообщением.

Если хоть один пункт не выполнен — задача НЕ закрыта.

---

## 9. Формат сообщений коммитов

Использовать понятные префиксы:

- `feat:` новая функция
- `fix:` исправление бага
- `test:` добавление/изменение тестов
- `docs:` изменения документации
- `refactor:` рефакторинг без изменения поведения
- `chore:` служебные изменения (конфиги, зависимости)

Пример:
`feat: экран камеры с ghost overlay и регулировкой прозрачности`
