# MAINTENANCE_AI — инструкция для ИИ поддержки и развития приложения

> Этот файл предназначен для ИИ, который будет СОПРОВОЖДАТЬ и РАЗВИВАТЬ
> ProgressPrivate после первичной разработки, включая возможную web-версию.
>
> Читать вместе с: CONSTITUTION.md, ARCHITECTURE.md, STACK_RESOLVED.md,
> TESTING.md, DOCS_TESTS_WORKFLOW.md, CODE_STYLE_RU.md, DECISIONS.md.
>
> Язык документации и комментариев — русский. Язык кода — английский.

## 1. Твоя роль

Ты — ИИ, отвечающий за долгосрочную поддержку и развитие продукта.
Твои задачи:

- исправлять баги;
- добавлять новые функции без нарушения приватностной модели;
- поддерживать актуальность зависимостей;
- обновлять документацию;
- при необходимости — развивать web-версию.

Ты работаешь так же дисциплинированно, как разработчик первичной версии:
маленькими шагами, с тестами, с проверками, с честной фиксацией результата.

## 2. Незыблемые правила (наследуются из CONSTITUTION.md)

Эти правила НЕЛЬЗЯ нарушать даже ради новой функции:

1. Фотографии и метаданные не покидают устройство.
2. Нет рекламных SDK.
3. Нет аналитики и трекинга.
4. Нет облачного AI/ML.
5. Нет облачного бэкапа по умолчанию.
6. Экспорт в галерею — только по явному действию пользователя.
7. Нет сетевого слоя для пользовательского контента.

Если новая задача противоречит этим правилам — остановись и запроси
явное решение владельца продукта. Зафиксируй решение в DECISIONS.md.

## 3. Порядок работы над задачей поддержки

1. Прочитать якорные файлы и последнюю запись в PROGRESS.md.
2. Понять и воспроизвести проблему (для багов) или уточнить требование
   (для новых функций).
3. Для багов — использовать методичный дебаггинг:
   - воспроизвести;
   - локализовать;
   - написать тест, который падает на баге;
   - исправить;
   - убедиться, что тест проходит.
4. Для функций — сначала план, потом TDD, потом реализация.
5. Обновить документацию (см. раздел 6).
6. Прогнать проверки (typecheck, lint, test, expo-doctor).
7. Тестовый запуск (для UI/native).
8. Обновить PROGRESS.md и при необходимости DECISIONS.md.
9. Коммит с понятным сообщением.

## 4. Управление зависимостями

- Обновлять зависимости инкрементально, по одному SDK/major за раз.
- Для Expo-совместимых пакетов использовать `npx expo install`.
- После обновлений запускать `npx expo-doctor` и полный набор тестов.
- Фиксировать фактические версии в STACK_RESOLVED.md.
- Не доверять памяти о версиях — источник истины это package.json
  и node_modules.

### Обновление Expo SDK

1. Прочитать changelog целевого SDK.
2. Обновить пакет expo, затем `npx expo install --fix`.
3. Проверить breaking changes для Reanimated, Gesture Handler, Router, MMKV.
4. Прогнать тесты и тестовые запуски на iOS и Android.
5. Зафиксировать изменения в DECISIONS.md и STACK_RESOLVED.md.

## 5. Как безопасно добавлять новые функции

Перед реализацией задай себе вопросы:

- Не требует ли функция отправки данных в сеть? Если да — конфликт с правилами.
- Не добавляет ли функция трекинг? Если да — запрещено.
- Можно ли реализовать локально/on-device? Предпочтительно да.
- Не усложняет ли функция проверяемость приватности?

### Пример: on-device ML (будущее развитие)

Если добавляется умное выравнивание фото:
- модель выполняется ТОЛЬКО на устройстве;
- фото не отправляются на сервер;
- использовать Core ML / ML Kit / TensorFlow Lite (on-device);
- зафиксировать решение и обоснование приватности в DECISIONS.md.

### Пример: IAP (поддержка/premium)

- Разрешено взаимодействие с Apple/Google для покупок.
- Даже при этом пользовательский контент (фото) не уходит на сервер.
- Обновить README.md и README_staff.md.

### Добавление нового визуального оформления (без дублирования экранов)

Приложение использует ОДНО дерево экранов и три визуальных стиля
(`modern`/`simple`/`neumorphism`). `modern` внутри платформенно-адаптивен:
iOS — Liquid Glass, Android — Material 3. Мы намеренно НЕ держим Liquid Glass,
Material и Gallery отдельными темами — пользователь выбирает «Современный»,
приложение само выглядит нативно под платформу. Новое оформление:

1. Добавить `DesignThemeId` в `src/models/settings.ts`.
2. Добавить определение (label, description, `previewLight`/`previewDark`) в
   `DESIGN_THEMES` и ветку в `resolveDesignTheme(id, scheme, platform)`
   (`src/theme/design-themes.ts`).
3. Включить его в `getPlatformThemeIds()`. Если нужен платформенный дефолт —
   поправить `getDefaultDesignThemeId()` и `migrateDesignThemeId()` (если нужна
   миграция старых значений).
4. Компоненты уже читают токены через `useAppTheme()` — новых копий экранов НЕ нужно.

Что НЕЛЬЗЯ делать:

- Не менять тип навигатора по теме (JS Tabs → NativeTabs).
- Не добавлять `key={designTheme}` к Provider/Stack/Tabs/спискам.
- Не размножать native GlassView в каждой ячейке списка.
- Не делать темы paywall'ом.
- **Не ломать platform defaults и миграцию**: iOS/Android → `modern`, web → `simple`;
  явный пользовательский выбор всегда важнее дефолта.

### Жесты камеры, compare и нижнее меню

- Свайп вкладок (`main-tab-swipe-gesture.tsx`) намеренно НЕ применён к Камере.
  Жестовые колбэки, вызывающие setState/router/haptic, — с `runOnJS(true)`.
- Tap-to-boost призрака (камера) — `Gesture.Tap` на слое ПОД контролами, поэтому
  не срабатывает на нижнем меню, затворе, кнопке «Эталон», слайдере, грид-тоггле,
  селекторе проекта и модалках (они выше по z-index).
- Pan-слайдер сравнения (`compare-slider.tsx`) — `Gesture.Pan` внутри
  `GestureDetector`; он живёт в стеке проекта, где нет свайпа вкладок, поэтому
  конфликт исключён. НЕ добавлять на compare screen сохранение/экспорт изображения.
- Нижнее меню (`main-tab-bar.tsx`) — центральная кнопка камеры/затвора; съёмка
  запускается через `camera-shutter-bridge.ts` (камера регистрирует обработчик),
  а не через проброс пропсов через навигацию.

### Как не сохранять временное состояние камеры

- Временное усиление призрака (`isBoosted`) — локальный `useState`, НЕ пишется в
  MMKV и НЕ идёт в `settingsStore`. Не добавлять его в `AppSettings` и в
  `DEFAULT_SETTINGS`.
- Сбросы временного состояния обязательны на: съёмку, смену проекта, уход с экрана
  (`useFocusEffect` cleanup), фон (`AppState`), смену источника эталона, ползунок.

### Работа с optional-полями фото и проекта

- `PhotoMetadata.note/isFavorite/isHidden` и `Project.referenceMode/referencePhotoId`
  — optional (safe migration). Старые записи читаются без физической миграции файлов.
- Отсутствие `note`/`isFavorite`/`isHidden` трактуется как пусто/false/false.
- `isHidden` НЕ удаляет файл и метаданные; скрытое фото исключается из timeline и
  авто-выбора first/latest/reference. Не путать скрытие с удалением (delete —
  отдельное destructive-действие с подтверждением).
- `referenceMode` отсутствует у старых проектов → `latest` (резолвер
  `resolveReferencePhoto` в `src/utils/reference.ts`).

### Тактильный отклик

- Единственное место импорта `expo-haptics` — `src/utils/haptics.ts`
  (`triggerHaptic(type, enabled)`). Не импортировать `Haptics` в экранах.
- Проверка: при `hapticsEnabled=false` вызовы no-op; на web/unsupported — no-op
  без падения (try/catch).

## 7. Развитие web-версии

Если принято решение о web-версии, учитывай следующее.

### Технологическая основа

- Expo и React Native поддерживают web через react-native-web.
- Expo Router работает и на web (file-based routing, universal links).
- Многие компоненты gluestack-ui совместимы с web.

### Что переносится легко

- Навигация (Expo Router).
- UI-компоненты и дизайн-токены.
- Бизнес-логика в /src/store и /src/utils (платформо-независима).
- Модели данных.

### Что требует отдельного решения (native-специфика)

- Камера: `expo-camera` на web имеет ограничения; ghost overlay поверх
  веб-камеры нужно проектировать отдельно (getUserMedia + canvas).
- MMKV: НЕ работает на web. Нужен альтернативный локальный storage
  (например, IndexedDB), но с сохранением принципа локальности.
- Биометрия: на web иная модель (WebAuthn), реализуется отдельно.
- Файловая система: на web нет sandbox как на мобильных;
  хранение фото на web требует продуманного локального решения.
- Уведомления: web push отличается от локальных мобильных уведомлений.

### Критично для приватности на web

- Web-браузер по своей природе менее «песочный», чем мобильный sandbox.
- Нельзя обещать на web ту же степень локальности без анализа.
- Любое хранение в браузере должно оставаться локальным (IndexedDB),
  без отправки на сервер.
- Обязательно зафиксировать в DECISIONS.md, какие приватностные гарантии
  сохраняются на web, а какие отличаются от мобильной версии.

### Архитектурный подход к web

- Выносить платформо-зависимый код за интерфейсы (storage, camera, auth),
  чтобы web и mobile реализовывали один контракт по-разному.
- Пример: интерфейс `PhotoStorage` с двумя реализациями —
  mobile (file-system) и web (IndexedDB).
- Общую бизнес-логику держать платформо-независимой.

## 8. Мониторинг качества (без нарушения приватности)

- НЕ добавлять аналитику пользователей ради «метрик».
- Ошибки и краши можно логировать ЛОКАЛЬНО и показывать пользователю
  опцию отправить отчёт вручную (по явному согласию), без автоматической
  фоновой отправки.
- Любая телеметрия — только opt-in и без пользовательского контента.

## 10. Когда обязательно остановиться и спросить владельца

- Изменение затрагивает приватностную модель.
- Требуется сетевой запрос с пользовательским контентом.
- Нужно добавить аналитику или рекламу.
- Крупное обновление SDK с breaking changes.
- Запуск web-версии с иными приватностными гарантиями.
- Замена ключевой библиотеки (MMKV, camera, router).

Во всех этих случаях: не действуй молча, зафиксируй варианты в DECISIONS.md
и получи явное решение.
